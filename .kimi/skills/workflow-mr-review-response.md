# MR Review 反馈处理工作流

> 收到 MR Review 反馈后的受控处理流程。核心理念：**先评估再动手、分类处理、条条有回音**。

## 触发条件

用户说以下任意一种时触发本规则：
- "处理 review"
- "review 反馈"
- "MR 反馈"
- "处理评论"
- "review 反馈评估"
- 提供了 MR 链接并要求处理 review 意见

---

## HARD-GATE 规则

**评估阶段绝不碰代码**。在用户确认评估结果之前：
- ❌ 不修改任何源代码文件
- ❌ 不执行 git commit / git push
- ✅ 可以搜索代码库理解上下文
- ✅ 可以用 `sequential_thinking` 分析反馈影响

---

## 工作流程

### Phase 0: 拉取评论

1. 从用户输入或当前工作状态获取 `project_id` 和 `merge_request_iid`
2. 调用 `gitlab_proxy(action="list_discussions")` 获取所有讨论线程
3. 调用 `gitlab_proxy(action="get_mr_diffs")` 获取最新代码变更
4. 过滤：跳过已 resolved 且无新增回复的线程
5. 输出评论摘要（仅用于内部理解，不修改代码）
6. 进入 Phase 1

### Phase 1: 评估分类

对每条未解决的 discussion，评估后标注分类：

| 分类 | 含义 | 后续动作 |
|------|------|----------|
| ✅ **接受** | 反馈合理，需要修改 | 改代码 → 回复 → resolve |
| ❌ **拒绝** | 反馈不适用或有误 | 回复理由 → 等对方确认 |
| ❓ **讨论** | 需要与 reviewer 进一步沟通 | 回复提问 → 等共识 |
| ⏭️ **延后** | 反馈合理但不属于本次 MR 范围 | 记录到 TODO → 回复说明 |

评估维度：
- **正确性**：反馈指出的代码问题是否确实存在？
- **影响范围**：修改会波及多少文件/模块？
- **紧急度**：是否属于 Critical/Blocker？
- **归属**：是否属于本次 MR 的职责范围？

#### 评估输出模板

```markdown
## MR Review 反馈评估 [!{iid}]

| # | 文件 | 行号 | 摘要 | 分类 | 复杂度 | 说明 |
|---|------|------|------|------|--------|------|
| D1 | path/to/file | L42 | 变量命名不规范 | ✅ 接受 | 低 | 改个名字 |
| D2 | path/to/file | L108 | 架构耦合问题 | ✅ 接受 | 高 | 涉及3个模块重构 |
| D3 | path/to/file | L15 | 建议用新模式 | ❓ 讨论 | - | 需确认是否适用 |
| D4 | path/to/other | L7 | 应增加容错 | ❌ 拒绝 | - | 该场景不会发生 |

**修改预估**：低复杂度 N 条，高复杂度 N 条
**建议路由**：[直接修改 / 建议 spec-driven]
```

**完成后暂停，等用户确认评估结果。**

### Phase 2: 用户确认

1. 展示评估表
2. 用户可能调整分类（如将"拒绝"改为"接受"，或标记某些项延后）
3. 确认后进入 Phase 3

### Phase 3: 执行修改

#### 复杂度路由

| 复杂度 | 判断标准 | 路由 |
|--------|----------|------|
| **低** | ≤3 文件，逻辑清晰，无跨模块影响 | 直接修改 |
| **高** | ≥3 文件，或多模块，或架构影响 | 暂停，建议 spec-driven |

#### 低复杂度修改

逐条处理"接受"类反馈：

1. 用 `job_create` 创建修改任务
2. 搜索代码库理解上下文
3. 修改代码
4. `job_update` 标记完成
5. 进入下一条

#### 高复杂度修改

1. 输出以下模板并暂停：
```
⚠️ 高复杂度反馈：D{N} 预计涉及 {X} 个文件/模块的改动。

建议启动 spec-driven 工作流处理此反馈：
- 输入"启动 spec-driven" → 规划后执行
- 输入"直接改" → 按低复杂度流程处理（风险自担）
- 输入"延后" → 标记为延后，本次不处理
```

2. 等用户决策后继续

### Phase 4: 回复关闭

每条 discussion 必须有回复，**禁止遗漏**。

| 分类 | 回复模板 | resolve |
|------|----------|---------|
| ✅ 接受 | `已修改，见 {commit_sha}` | ✅ 自行 resolve |
| ❌ 拒绝 | `此处因 {理由} 保持现状，{补充说明}` | ❌ 等对方确认后再 resolve |
| ❓ 讨论 | `关于这个问题，{提问/说明}` | ❌ 等共识后 resolve |
| ⏭️ 延后 | `同意，但不在本次 MR 范围内，已记录到 TODO` | ❌ 等对方确认 |

工具调用：
```
gitlab_proxy(action="add_reply", discussion_id, body="回复内容")
gitlab_proxy(action="resolve_thread", discussion_id)  # 仅接受类
```

### Phase 5: 推送验证

1. `git add` + `git commit` 修改的文件
2. `git push` 推送到 MR 源分支
3. 确认所有"接受"类 discussion 已 resolved
4. 输出处理摘要

---

## 禁止操作

| 操作 | 约束 |
|------|------|
| ❌ 评估阶段修改代码 | 必须等用户确认评估结果 |
| ❌ 自行 resolve 有异议的线程 | 必须等对方确认 |
| ❌ 自行 Approve MR | 必须用户明确许可 |
| ❌ 修改 MR 描述 | 未经用户允许 |
| ❌ 遗漏 discussion 不回复 | 每条都必须有回音 |

---

## 与其他工作流的关系

```
MR Review 反馈处理
├── 低复杂度反馈 → 直接修改（本工作流完成）
├── 高复杂度反馈 → 建议 spec-driven（跳转双文件工作流）
└── 需要重新 review → 建议 hmirp-code-review（跳转审查 Skill）
```

| 场景 | 来源 | 跳转目标 | 触发条件 |
|------|------|---------|---------|
| 高复杂度修改 | 本工作流 Phase 3 | spec-driven | 修改涉及 ≥3 文件/多模块 |
| 修改后需再审查 | 本工作流 Phase 5 | hmirp-code-review | 用户要求 Re-review |
| 审查完收到反馈 | hmirp-code-review | 本工作流 | MR 被评论 |
| spec 产出 MR 收到反馈 | spec-driven | 本工作流 | MR 被评论 |

## 指令速查

| 场景 | 用户说的 | Codely 行为 |
|------|----------|-------------|
| 触发 | "处理 review" / "review 反馈" | 拉取评论 → 评估分类 |
| 确认评估 | "评估 OK" / "按这个改" | 执行修改 |
| 调整分类 | "D2 改成延后" | 更新评估表，重新确认 |
| 跳过复杂项 | "延后" | 标记延后，不处理 |
| 走 spec | "启动 spec-driven" | 跳转双文件工作流 |
| 完成修改 | "改完了，推吧" | push + 回复讨论 |
